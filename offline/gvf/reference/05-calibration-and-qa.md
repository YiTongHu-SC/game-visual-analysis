# 05 · 校准、验收与保留可讨论地带

版本：GVF 0.2.0；核验日期：2026-10-21。本章是**待实测的校准工作协议**；样本量、分档容差和示例预算均为提案。当前81参数，历史0.1.0的78项快照保留。四游戏12张官方截图已经做证据限定的观察，但未做同样本双人独立评分、玩家测试或动态试玩。

本文的 QA 记录格式与状态是工作流程建议。当前 profile／CLI 只实现其中一部分，具体对照见 [03 · 概念规范与本版合同](03-parameterization.md#0-概念规范与本版-jsoncli-的边界)；不要把本文建议字段当作可以随意增加的 profile 属性。

本轮[真实案例](10-real-game-validation.md)由AI分担拆解并整合复查，不能称为下面第4/5节的一致性实验。截图来源、ROI、逐参数unknown与文件关联可以复核；这不证明序数判断已共同校准、游戏完整覆盖或可读性达标。`visual_observation`是证据描述，`design_profile`才表达未来制作规则，二者的状态和验证结果不互换。

## 1. 一致性来自共享证据，不来自数字精度

两个人都说“写实度 40”，不表示他们对同一张图的理解相同。应验证他们能否在相同条件下：识别相同参数、引用相同参考、指出同一处偏差，并提出方向一致的修改。

框架的验收分成四层，分别报告，不能合并成一个“通过率”遮住缺口。

| 层 | 回答的问题 | 可用证据 |
| --- | --- | --- |
| 数据完整性 | 文档是否可被工具解释、字段是否合法 | schema／语义校验、单位与引用检查 |
| 视觉一致性 | 结果是否符合约定的形体、颜色、线条和材料 | 对齐视图、参考板、评审标注、源工程检查 |
| 交互有效性 | 玩家是否识别主角、敌人、目标和关键状态 | 真实游戏片段、任务成功／误判记录、玩家测试 |
| 技术与无障碍 | 是否在目标设备、显示和设置中有效 | 性能剖析、最低规格运行、对比检测、减动／高对比模式、专门测试 |

一个 JSON 能被解析，只证明第一层的一部分；一张精致截图也不证明另外三层通过。

## 2. 在打分前锁定观察合同

每个风格profile建立明确的观看与测量约定。下表是外部QA记录建议，不能当作新增 `observation_contract` 字段塞入profile，也不等同0.2的 `visual_observation` 文件类型。后者专门记录所列官方截图的来源、局部ROI、方法和限度；它没有伪造截图的运行上下文。

| 类别 | 需要记录 |
| --- | --- |
| 身份与版本 | profile 版本、资产／游戏构建提交、引擎与渲染器版本、参考板版本、测试日期 |
| 输出与显示 | 最终宽高、纵横比、内部渲染比例、升采样／AA、SDR／HDR、色空间、显示设备及已知校准状态 |
| 观看条件 | 1:1 输出观看／缩略图／放大细节各自用途、窗口缩放、屏幕尺寸、常用距离、室内亮度是否已控制 |
| 相机与遮罩 | 镜头 ID、投影、FOV 轴或正交范围、对象占高、裁切坐标、主体／背景／UI 遮罩 |
| 光照与颜色 | 测试光照 ID、曝光模式、颜色管理配置／观察变换、是否已烘焙、后期强度 |
| 时间与状态 | 场景／关卡、动作／特效状态、时间码／帧号、录制帧率、真实游戏速度、随机种子（如可用） |
| 测量 | 工具与版本、采样位置、分位数／计数方式、舍入显示与实际比较精度、测量限制 |

没有显示仪器时写“显示器未做仪器校准”，仍可做限定设备上的相对比较。不要为了填满表格虚构色温、屏幕亮度或校准状态。

## 3. 参考板要能回答“借鉴哪一部分”

每条参考保存：`reference_id`、来源链接、作者／发行方、获取日期、图／视频时间码、使用范围、裁切、观察条件、目标参数、赞同点、排除点、授权／仅链接说明。网页变化或素材不可访问时，记录缺口；不要用未经许可的素材副本填补归档。

建议同一轴至少保留：

- **正例**：目标区间中可接受的多个实例，避免把风格简化成单张图片的构图。
- **反例**：只偏离一个关键规则的实例，并明确失败原因。
- **边界例**：相邻锚点之间或可讨论区间内的实例，用来检验大家是否理解边界。
- **例外**：因叙事、交互或无障碍需要而允许偏离的实例，记录适用范围。

不要用某一款游戏的全部画面隐含定义多个轴。可以借鉴 A 的外轮廓、B 的调色层级、C 的动作时序，但必须单独解释冲突如何处理。不同作品截图不得在不同亮度、裁切和缩放下直接比较线宽或细节密度。

### 3.1 每个候选资产至少保留两种视图

**规范视图**固定对象、尺寸、背景、光照和颜色管理，用于比较结构与材料；**游戏视图**放入实际镜头、关卡、UI 和特效，用于验证真实观感与信息组织。规范视图合格不能替代游戏视图合格。

对 2D／像素项目，规范视图可以是原生逻辑像素、规定整数放大和中性底色；对 3D，通常包含正／侧／背或转台、一个受控光照和实际关卡。视图数量由资产用途决定，不能机械地要求所有项目拍同样的三视图。

## 4. 两个人如何校准

以下为可立即执行的一轮小规模试运行，所有数量和阈值均可调整；它们不是行业认证或统计可靠性保证。

1. **选择任务**：只先校准 5–8 个会影响本轮生产的轴，确定对象类别、目标镜头与规则优先级。不要同时评完所有参数。
2. **制作校准包**：准备约 12 个样本，覆盖低／中／高锚点、正／反例与边界。预先划分讲解样本和保留样本，保留样本不参加锚点讨论。
3. **独立标注**：两位评审先不交换结论，各自记录分档／区间、参考 ID、可见证据、未知项、硬规则失败点及建议修改。不要求他们猜源工程参数。
4. **定位分歧**：按字段与样本比较。先判定是术语不同、观察条件不同、样本处于边界、证据缺失，还是审美偏好不同；不能直接平均两个分数掩盖争议。
5. **修订锚点**：把最有区分力的裁切、反例和一句边界规则加入参考板，记录版本变化；允许原先过宽的一个轴拆成两个。
6. **盲测保留样本**：重新独立评估。可先采用“同档或相邻已批准区间，且数值标签差不超过 10”为内部调查触发线；超过就复查。该 10 分是工作约定，不能解释为感知等距或科学误差。
7. **检查修改方向**：两位评审分别给修订指令，核对是否指向相同可执行变化。能猜中相同分数，却提出相反修改，说明沟通仍未校准。
8. **冻结本轮版本**：记录参与者、样本清单、逐项分歧、未解决问题和允许范围，再投入少量生产。换镜头、平台或核心模型时重新校准受影响部分。

最低报告应包含每项的同档比例、分歧样本列表和硬规则一致／不一致清单；可辅助报告同一序数标签下的差值分布，但不能据此宣称等距测量。小样本报告不要伪装成总体准确率。需要研究级一致性结论时，应另行设计样本、评审数量、统计方法与不确定性分析。

## 5. 两个 AI 如何校准

沿用上述输入与保留样本，增加以下边界：

| 风险 | 执行约定 |
| --- | --- |
| 把措辞相同当理解相同 | 让 AI A／B 分别标出图中具体位置、引用锚点，再各自生成修改任务；检查任务执行后的变化 |
| 相互抄答案 | 首轮分开上下文，保存独立结果；讨论后再复测未见样本 |
| 相同模型偏差一致 | 记录模型供应方、模型 ID、版本／日期及可用设置；同一模型的两次调用不是两个独立专家 |
| 语言强于视觉 | 给出缩放、裁切和真实图像／视频；工具不支持视频或多视图时注明不可检查的项目 |
| 评分很精确但证据不足 | 限制为锚点／区间，要求列出可观察证据；不以模型自报 confidence 直接代替正确率 |
| 互相证明正确 | 人工检查关键硬规则与分歧样本，保留真实运行和源工程证据 |
| 跨工具参数失配 | 维护每个工具自己的适配说明；未经实测的提示词映射只标为假设 |

可设计两个任务：**解释测试**，让两者读同一资产并指出相同规则；**生成测试**，让两者依据同一 profile 产出不同资产，再由不看生成记录的评审判断是否同属一个系列。两者都通过，才获得比“提示词相同”更强的协作证据。

这仍不能保证“任意两个人或任意 AI 永远无歧义”。框架的可实现目标是降低歧义、暴露剩余分歧，并提供修订路径。

## 6. 硬规则、软规则、探索区与例外

| 类别 | 用途 | 不满足时 |
| --- | --- | --- |
| `hard` 硬规则 | 信息语义、明确技术约束、已批准的核心识别规则 | 阻止该范围的验收，或必须有批准且有效的例外 |
| `soft` 软规则 | 常规偏好、关系方向、目标区间 | 标记偏离并说明代价；允许有理由的取舍 |
| `exploratory` 探索区 | 尚无共识或故意保留的表达空间 | 不给单点通过／失败；比较候选、记录结论与下一步 |

这些强度是项目治理选择，不代表每一条外部建议自动成为硬规则。将来源建议升级为项目硬规则时，写清采纳范围和责任人。

### 6.1 状态与判定分开

参数的 `known`／`unknown`／`not_applicable` 描述信息状态；验收的 `pass`／`fail`／`needs_review`／`not_tested` 描述检查状态。两种状态不能共用一个布尔值。

此处 `known` 是概念说明；本版 JSON 的对应写法是 `state: "set"`。当前 profile 只允许有限的状态字段，上述完整 QA 结果单独保存，不向其新增枚举。

- `unknown`：确有这个变量，但没有足够证据，例如截图无法确定原始粗糙度。
- `not_applicable`：变量在当前范围无对象，例如正交相机的透视 FOV；写理由。
- `known`（JSON 为 `set`）：有足够证据陈述目标或观察；不代表结果自动通过。
- `not_tested`：尚未执行检查；不能算通过，也不能填 N/A 回避。

### 6.2 例外不修改整个风格定义

例外记录应包含：`exception_id`、被覆盖的规则 ID、对象／场景范围、偏离的值、理由、替代检查、责任人、有效版本／截止时间和是否需要回归测试。例如“Boss 最终阶段可打破常规轮廓颜色，但攻击方向仍由独立形状与时序表达”。

不能用“艺术需要”作为无限通行证。例外必须足够具体，使另一个人或 AI 知道何时可以使用、何时不可以使用。某种例外反复出现时，重新判断它是否应成为正式的子 profile。

### 6.3 怎样保留少量模糊地带

把“可爱但略古怪”“粗粝但温暖”等意图保留为讨论层，链接到已确定的形体、色彩和边缘约束，并列出尚待比较的候选。可采用如下记录：

```text
问题：工具表面的磨损应让人感到“被长期使用”，而非“肮脏”
已冻结：主体轮廓、功能色、整体材质类别
开放：磨损分布与局部色差；提供 A/B/C 三个候选
边界：不降低识别距离，不把危险色用于普通污渍
决策：由指定美术负责人看实际游戏尺寸选择；未选前不写成生产硬规则
```

模糊区也有输入、允许变化、禁止越界和决策方式。它保留审美判断，同时避免 AI 为求“完成”而自行补造答案。

## 7. 视觉与交互验收采样

下面是覆盖清单，按玩法裁剪；每项记录已测／未测和适用性。项目可以先从一个角色、一个环境块、一个 UI 面板和一个核心特效建立最小验收切片。

| 维度 | 至少考虑的样本 | 关注的失败 |
| --- | --- | --- |
| 尺度 | 主要游戏距离、最远有效距离、近景；最低／目标输出分辨率 | 细节糊成噪声、内线合并、像素网格破坏 |
| 明暗 | 亮背景、暗背景、过渡曝光；实际常见光照 | 轮廓丢失、信息色与环境融合 |
| 形体与对象 | 同类多资产、不同朝向、相邻放置、不同体型 | 风格漂移、敌我／交互类别混淆 |
| 动态 | 待机、移动、相机平移、攻击、命中、最大特效叠加 | 笔触滑动、时序模糊、闪烁、目标被遮挡 |
| UI 状态 | 常态、选中、焦点、禁用、错误、字幕；最长本地化文本 | 信息层级塌陷、焦点不可见、文字被裁切 |
| 可访问设置 | 高对比、减动、字号／字幕、颜色替代和输入差异 | 关键语义丢失、设置只改装饰未改变障碍 |
| 设备与模式 | 最低设备、常用设备；窗口比例、掌机／电视／VR（适用时） | 显示尺寸与预算失配、边缘裁切、视场不适 |

**可读性**不是“看得出很好看”。每种关键信息定义一个观察任务，例如“在规定距离和运动中判断哪个对象可交互”“识别攻击方向并在窗口内响应”。记录参与者、成功／误判、反应时间和观察限制；试运行前的数值只能叫目标，不能写成实测结果。

灰度、模糊缩略图、色觉模拟和遮罩诊断都是发现问题的辅助视图，不是玩家体验的替代品，也不自动证明色觉障碍人群可用。

## 8. 对比度、无障碍与视觉风格的边界

### 8.1 标准适用范围要明确

**来源事实**：WCAG 2.2 的普通文字对比阈值为 4.5:1，符合其大文字定义时为 3:1；必要非文字组件／图形的信息部分一般为 3:1，并存在范围和例外。[B03 · 文字](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[B04 · 非文字](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

这些规则直接针对 Web 内容。本框架将它们用于网页与类似 UI 的清晰度检查；游戏项目应再指定采用哪些游戏／平台规范。**不能用全屏平均对比度，或要求场景中每对相邻像素都达到 3:1，来验收一整幅写实／绘画游戏画面。**

**来源事实**：XAG 102 给出游戏中的文字／视觉元素及高对比模式建议，并按平台区分“大文字”，要求复杂背景取最低对比区域；与 WCAG 的禁用元素处理也不同。[B05 · XAG 102](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/102)

因此项目QA应记录对比度策略的来源与版本，例如“网页报告按WCAG，游戏UI按本项目采纳的XAG 102范围”；profile可通过理由或参考关联，不新增未经schema支持的 `contrast_policy` 属性。不要把多个标准拼成无出处的统一门槛。引用XAG不等于完成Xbox认证或合规审计。

### 8.2 检查真实的信息对

建议列出 UI token／状态的前景—背景对，并检查动态场景中最不利的背景。透明文字底板先正确合成，再计算对比；不能只用未合成的名义色值。

**来源事实**：WCAG 的 sRGB 相对亮度使用线性化 RGB 的加权值，对比度公式基于相对亮度而非 OKLCH L。[B14 · WCAG 定义](https://www.w3.org/TR/WCAG22/#dfn-relative-luminance)

工具可以对已知 token 做静态筛查，但仍要实际查看字体笔画、输出尺寸、动画遮挡和不同背景。名义色值通过，不能保证细线小字实际清晰；HDR、非 sRGB 或复杂透明／后期输出需要相应测量流程。

### 8.3 语义不只依赖颜色

**来源事实**：XAG 103 建议用多种感官渠道表达关键提示，并考虑色觉差异。[B06 · XAG 103](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)

本框架把“危险”“可交互”“锁定”“稀有度”等语义与颜色 token 分开；按玩法增加形状、图标、位置、运动模式、文字、声音或触觉。高对比和颜色替代模式可以改变默认配色，但应保留这些语义关系。

### 8.4 时间与舒适度不能用静态截图验收

**来源事实**：XAG 117 涵盖动态 UI、相机摇晃／晃动、模糊和视场等设置；XAG 118 要求检查光敏相关内容，关注闪烁及空间图案等因素。[B07 · XAG 117](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/117)、[B08 · XAG 118](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/118)

本框架要求在真实速度片段与运行构建中检查上述内容，保留减动／关闭相关效果的规则。没有完成专门评估时写“光敏风险未专门验证”，不能凭“低于某个单一频率”“没有主动做闪光”或一张截图宣称安全；也不能以一条开场警告替代问题修复。一般颜色／schema 脚本不具备这类验证能力。

## 9. 性能与制作约束也进入验收

视觉规范应附平台预算，但不把性能成本当作画风定义。例如“低多边形”是形体表达或资产约束；总三角形数低，仍可能因透明叠加、着色器、阴影和带宽超过预算。

预算建议写：设备型号、输出与内部渲染比例、目标 fps、CPU／GPU 的 ms 预算、内存／显存、纹理尺寸、draw calls／批次、过度绘制、特效峰值数量、加载限制与降级策略。60 fps 对应的总显示周期约为 16.67 ms；它不是可以重复分配给每个渲染 pass 的预算，CPU 与 GPU 的重叠也须按引擎剖析解释。

测试记录应包含构建版本、场景、设备、电源／热状态、采样时长、工具及 P50／P95 等统计定义。未运行目标设备时只能报告预算建议或已运行设备上的结果；不能由截图估算真实 GPU 时间，不能由通过 JSON 验证推出运行性能通过。

## 10. 谁来决定什么

| 角色／职能 | 主要责任 | 小团队可合并的部分 |
| --- | --- | --- |
| 美术负责人 | 冻结视觉意图、参考锚点、软规则取舍、审美例外 | 用户本人可以兼任，但要区分本次决定与长期规则 |
| 技术美术／渲染 | 工具适配、颜色管理、材质／线条实现、技术预算 | 程序员兼任；对无实际测量的数值标未知 |
| 设计／UX | 信息层级、战斗／交互时序、识别任务 | 开发者兼任；用真实玩法复核 |
| QA／无障碍评审 | 按合同运行检查、记录失败、验证设置 | 不应只由资产生成者自评；需要时引入相关玩家／专业评估 |
| AI 助手 | 整理规范、候选生成、可追溯标注、运行有能力的检查 | 不自行宣称未执行的视觉／性能／无障碍测试通过 |

一人团队也可以按不同职能分轮检查，保存判断依据。角色表不要求增加团队规模，而是防止“谁都以为别人已经验过”。

## 11. 最小 QA 记录与发布状态

每条检查记录至少包含：规则 ID、测试资产／构建、观察合同 ID、检查者与工具、结果、证据路径／时间码、发现、下一步和例外 ID（若有）。图片中的标注要保留原帧，并说明裁切／放大，避免只交付失去上下文的局部。

对单个范围的最终状态建议采用：

- **通过**：已执行所有适用硬检查；软规则偏离有说明；所有例外有效；不把未测项目计入。
- **待复核**：存在无法判断的硬约束、重要观察条件不明或评审分歧。
- **失败**：至少一个适用硬规则不满足且没有有效例外。
- **试验中**：profile 或探索区尚未冻结，只能用于候选比较。

当前0.2.0仍标为“可试运行”。本轮四例12图用于发现定义、范围与可观测方法的缺口，不是12个已批准校准样本；也未实施上述保留样本盲测。后续真实制作项目需补齐同条件锚点、独立评分、真实速度回放和玩家任务。结构与证据关系校验不能替代这些实证工作。
